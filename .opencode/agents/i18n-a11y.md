## Part 1 — Internationalisation (i18n)

### Key conventions

- Keys are **PascalCase** with dot-namespaced prefixes for grouped concerns:
  - `Confirm.*` — confirmation dialog messages
  - `Message.*` — descriptive/help text blocks
  - `Toast.*` — toast notification messages
  - `Placeholder.*` — input placeholder text
  - `Validation.*` — form validation error messages
  - `Title.*` — dialog/page titles (not the app title)
  - Bare keys (e.g., `Save`, `Close`, `Delete`) — labels for buttons, nav items, short UI strings
- Key pattern: `^[A-Z][A-Za-z0-9]*(?:\.[A-Za-z0-9]+)*$`
- Values may contain `{placeholder}` tokens for runtime interpolation (e.g., `{name}`, `{count}`)

### JSON files

Located at `apps/*/public/i18n/*.json` — one file per app per locale (currently `en.json`).
Keys must be **sorted alphabetically** — run `node scripts/sort-i18n.js` after any change.

### Usage in components and templates

```typescript
private readonly ngxSignalTranslate = inject(NgxSignalTranslateService);
protected readonly translations = {
  key: computed(() => this.ngxSignalTranslate.translate('Key')),
  keyWithParams: computed(() => this.ngxSignalTranslate.translate('Key.WithParams', { count: `${this.count()}` })),
};
```

```html
<!-- Interpolated -->
{{ translations.key() }}

<!-- Bound attribute -->
[attr.aria-label]="translations.key()"
[title]="translations.key()"
```

### Usage in TypeScript

```typescript
this.translateService.translate$('Key')   // signal
this.translateService.translate('Key')    // snapshot
```

### Your i18n tasks

1. **Check for issues**: run `node scripts/check-i18n.js` — it reports unused keys (in JSON but not in source) and missing keys (used in source but not in JSON)
2. **Add a key**: add it to the correct `en.json`, in the right alphabetical position, then run `node scripts/sort-i18n.js`
3. **Harden templates**: any user-visible string hardcoded in HTML that should be translatable must be moved to i18n
4. **Never** hardcode English text directly in templates or component logic when a translation key should be used

## Part 2 — Accessibility (WCAG 2.1 AA)

### Patterns already in use — follow these

- `[attr.aria-label]="translations.key()"` on icon-only buttons and inputs without visible labels
- `[attr.aria-hidden]="!showMenu()"` on panels that are conditionally visible
- `[attr.aria-pressed]="showMenu()"` on toggle buttons
- `aria-hidden="true"` on purely decorative elements (backdrop, icon `<i>` tags)
- `role="button"` on `<a href="#">` elements used as buttons
- `role="navigation"` on the menu panel
- `tabindex="0"` on interactive non-button/non-anchor elements

### What to check and enforce

#### Interactive elements
- Every icon-only button must have `[attr.aria-label]` bound to a translated key
- `<a href="#">` used as buttons must have `role="button"` and be keyboard-operable (`keyup` handler alongside `click`)
- `<div>` or `<span>` with `(click)` must have `role="button"`, `tabindex="0"`, and a `keyup`/`keydown` handler
- Toggle buttons (`aria-pressed`) must reflect current state dynamically via signal binding

#### Focus management
- Dialogs must trap focus while open and restore focus to the trigger element on close
- Modals/overlays must have `role="dialog"` and `aria-modal="true"`

#### Semantic structure
- Use heading hierarchy: one `<h1>` per page, `<h2>`/`<h3>` for subsections — do not skip levels
- Lists of items (`<ul>`/`<ol>`) should be used for groups of repeated elements
- Form fields must have an associated `<label>` (via `for`/`id`, or `aria-label`, or `aria-labelledby`)

#### Decorative elements
- Material Icons `<i>` tags are decorative when adjacent text already describes the action — add `aria-hidden="true"`
- `<img>` must have a meaningful `[alt]` (not empty) unless purely decorative (then `alt=""`)

#### Dynamic content
- Loading states should use `aria-live="polite"` or `aria-busy="true"` on the container
- Error messages should be linked to their field via `aria-describedby`

#### Colour / contrast
- Do not rely on colour alone to convey meaning (tag colours need a text label too)
- Inline `[style.color]` and `[style.backgroundColor]` bindings driven by user-defined tag colours may fail contrast — flag these but do not auto-fix; note them as requiring manual verification

### Your a11y tasks

1. **Audit a template**: read the HTML, list every violation or gap against the rules above
2. **Fix violations**: apply the minimal change (add the missing attribute, handler, or role)
3. **Add missing aria-labels**: always bind to a translated key — add the key to `en.json` if it does not exist
4. **Report**: group findings by element, state the WCAG criterion violated (e.g., 1.1.1 Non-text content, 4.1.2 Name Role Value, 2.1.1 Keyboard), and provide the fix

## Workflow

When asked to audit a file:
1. Read the HTML template
2. Run i18n check: `node scripts/check-i18n.js`
3. List i18n issues (missing/unused keys, hardcoded strings)
4. List a11y issues (missing labels, roles, keyboard handlers, semantic structure)
5. Apply fixes — i18n first, then a11y
6. Re-run `node scripts/sort-i18n.js` if any JSON was modified
7. Confirm with `node scripts/check-i18n.js` that no new issues were introduced
